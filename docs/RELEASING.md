# Releasing visual-omp

Changes are committed to `main` as conventional commits (`feat`, `fix`, `chore`, `docs`, `build`, `ci`, `refactor`, `style`, `test`). A push to `main` runs CI (typecheck, tests and an installer build on macOS and Windows) without publishing application installers. This repository also serves the Homebrew tap and the Scoop bucket, so a push that changes `Casks/visual-omp.rb` or `bucket/visual-omp.json` becomes available to Homebrew users through `brew update` and to Scoop users through `scoop update`, including a change for a version that is already released. New installers are published only when someone pushes a version tag, and the owner approves pushes and releases separately.

## Cutting a release

1. Move the entries under `## [Unreleased]` in [CHANGELOG.md](../CHANGELOG.md) into a new `## [X.Y.Z] - YYYY-MM-DD` section, and leave an empty `## [Unreleased]` heading above it. That section becomes the GitHub release notes word for word, so write it for the people installing the update.
2. Set the version without creating a tag: `npm version X.Y.Z --no-git-tag-version`.
3. Commit `CHANGELOG.md`, `package.json` and `package-lock.json` as `chore(release): vX.Y.Z`. Do not push or tag yet.
4. Give the owner a development build of that release commit: with a clean working tree, start `npm run dev`, which uses its own profile and runs beside an installed copy, and leave it open. Continue only after the owner has tried it and asked for the release. If the release commit changes, restart the development build on the new commit and obtain the owner's approval again.
5. Push `main`, then tag the exact commit the owner tested and push the tag: `git tag vX.Y.Z <tested-commit-sha> && git push origin vX.Y.Z`.

The tag starts [.github/workflows/release.yml](../.github/workflows/release.yml). It stops before building anything if the tag does not match `package.json` or if CHANGELOG.md has no section for the version, and it takes the release notes from the tagged commit, so later changes to `main` cannot alter them. After typecheck and tests pass, it builds the macOS disk images (Apple Silicon and Intel) and the Windows installer and publishes them as a GitHub release with the CHANGELOG section as the notes. For a stable version it also commits the updated Homebrew cask (`Casks/visual-omp.rb`) and Scoop manifest (`bucket/visual-omp.json`) to `main`, each with the SHA-256 checksum of its installer. A file that already offers a newer version is left as it is, with a notice in the run's summary, so a stable tag published after a newer one (a fix on an older line, or a re-run of an old release) still gets its GitHub release but never moves Homebrew or Scoop users back to it. The same version is written again so the cask and manifest use the checksums of the newly published installers. A version with a semver prerelease part (`1.2.0-beta.1`, `1.2.0-rc.2`) is published as a GitHub prerelease and leaves the cask and the Scoop manifest alone, so `brew upgrade` and `scoop update` never install it, and the in-app check only offers it to copies that are already running a prerelease.

The Scoop manifest does not run the NSIS installer. Scoop opens the installer with 7-Zip, unpacks the app archive inside it (`$PLUGINSDIR\app-64.7z`) and removes the installer's own files, so the Windows build feeds both install methods. A change to the NSIS packaging that renames or moves that archive also needs a change to `scripts/update-scoop-manifest.mjs`.

## How the update reaches users

Installed copies of visual-omp check GitHub for the newest release about ten seconds after they open and every 30 minutes while they stay open, and **Check for updates…** (the app menu on macOS, the Help menu on Windows) checks immediately. A result saved by an earlier session never stands in for the check at launch; within a session, Settings → About reuses a result younger than 30 minutes. Scheduled checks make about two GitHub requests an hour per running copy, plus checks at launch and on request. GitHub's unauthenticated limit is 60 requests an hour per IP address, shared with other clients. When a newer version is published, the app shows a notice with the first sentence of the release notes, and **Settings → About** offers the update. Homebrew is used only when the running app is the copy the cask installed: the app then runs `brew update` and `brew upgrade --cask visual-omp` in a terminal inside the app, confirms that the installed copy has a newer version, and restarts into it. The upgrade runs with `HOMEBREW_NO_ASK=1`, because Homebrew 6 and later otherwise stops at a `[y/n]` question in that terminal (its plan names the cask as `decoy-dev/tap/visual-omp`), and the click that started the update is the user's confirmation. Other macOS installs download the new disk image to Downloads and open it for the drag to Applications. On Windows, a copy that Scoop installed for the current user (its folder is `<scoop>\apps\visual-omp\…` with Scoop's install record beside the executable) quits and starts a PowerShell window. Scoop refuses to update an app while it runs, so that window waits for visual-omp to exit, runs `scoop update` and `scoop update visual-omp`, and opens visual-omp again. It stays open when Scoop did not install a version newer than the one that quit, or when visual-omp could not start, so the person can read what went wrong. A copy Scoop installed for all users (`--global`, found through `SCOOP_GLOBAL`, Scoop's `global_path` setting or `%ProgramData%\scoop`) needs an administrator to update, and visual-omp never asks for administrator rights, so its update window shows `scoop update visual-omp --global` to run instead. Any other Windows copy downloads the installer to Downloads, runs it and quits so it can replace the app, and its update window suggests switching to Scoop. Packaged builds download installers only from the release's own `github.com/decoy-dev/visual-omp/releases/download/…` link and GitHub's download servers. Releases publish no checksums, so the app does not verify the file beyond that; Homebrew and Scoop check their downloads against the checksums in the cask and the manifest. The first launch after an in-app update reports whether the new version started. Homebrew and Scoop users can also update from a terminal with `brew upgrade --cask visual-omp` or `scoop update visual-omp`, after quitting visual-omp in Scoop's case.

omp updates separately from visual-omp. The app runs `omp update --check` on the same schedule and offers to run `omp update`, and because each open chat keeps the omp version it started with, it then offers to restart those chats.

## Testing the update flow

No release has to exist to exercise these screens. Development builds (`npm run dev`, never a packaged app) read releases from the JSON file named by `VOMP_UPDATE_FEED` instead of GitHub. The file holds `releases` in the GitHub API shape, and optional fields simulate the rest: `method` (`brew`, `dmg`, `scoop`, `nsis` or `manual`), `brewCommand` (a harmless command runs by default), `installedVersion` (what the Homebrew check reads from the app on disk), `scoopGlobal` (a Scoop install for all users), `ompCheck` (`{ code, stdout, stderr }` in place of `omp update --check`), `ompUpdateCommand` (runs in place of `omp update`) and `ompVersionAfter`. Asset URLs may use plain http so a local server can stand in for GitHub. Development builds never restart themselves, so the Scoop restart itself can only be tested with packaged builds. Set `VOMP_DEV_PROFILE` to a directory name to run this instance beside another development instance.
