## Items

### 1. Tighter bundle ceiling (S)
The guard passes when growth over the v0.7.4 baseline (2,017,581 bytes) is at most 20,000 bytes or the entry is at most `acceptedGrowth.entryBytes` (2,044,096) (`scripts/guard-renderer-bundle.mjs:41-45`). The entry was 1,591,722 bytes after `33f694c`. `acceptedGrowth` can only raise the limit, so tightening means a rebaseline in `scripts/renderer-classic-baseline.json`, plus updates to `docs/ARCHITECTURE.md` and `docs/TSP-MIGRATION.md`.
- Recommended default: rebaseline on a measured production build at its exact commit (the `v0.7.6` tag if its build is measured, never an invented tag), keep the 20,000-byte growth allowance and remove `acceptedGrowth`.

### 2. Preview cross-origin header (S)
`src/main/services/preview-protocol.ts` sends `Access-Control-Allow-Origin: *` on every response, while the plan allows it for fonts only. Phase 2's plan lets this fix ship on its own, before any later slice.

### 3 and 7. Install method
- visual-omp already detects how it was installed (`detectInstallMethod`, `src/main/services/updates.ts:292`) and updates Homebrew and Scoop copies in the app. Windows installer copies show a guide to switch to Scoop (`ScoopSuggestion`, `src/renderer/src/features/onboarding/UpdateSheets.tsx:114`). macOS has no matching guide to the cask (S).
- The setup wizard runs omp's install script (`src/main/omp/locate.ts:13-14,36`). Offering Homebrew when `brew` exists is M. omp's updater recognizes Homebrew installs [17.3.4]; whether `omp update` on a Homebrew omp behaves in 18.16 is untested.

### 4. Phone or other computer (S to M, provisional)
omp 18.16 rooms are end-to-end encrypted, and my.omp.sh serves omp's browser client, which has a mobile layout. The app's Invite already publishes a control link and a view link (`src/main/features/collab.ts`, `ShareDialog.tsx`). The work would add a QR code, keep the Mac awake while a chat is shared, and publish again after omp rotates the room (`/new`, `/resume`, fork). The size stays provisional until the tests below pass. Exposing the app's own relay on the network (M to L) or a companion mobile UI (XL) cost far more. For another computer, `omp join <link>` already works.
- Feasibility tests: an iPhone on the control link (send, approve, Stop, lock and reopen the phone); the Mac sleeping during a share; the phone and the desktop answering the same question; a room rotation while the phone is connected.
- Owner: control or view link by default on phones; whether relying on omp's public relay is acceptable; keep the Mac awake while shared.

### 5. Close all chats (M)
Current chats are the `tabs` array, and `closeChat` asks only when omp or helpers are working; the quit dialog already lists every chat with work in flight and handles chats whose state is unknown (`quit.tsx`). The work adds `closeAllChats()`, a dialog kind that reuses the quit findings and also names drafts that would be lost, a header button or menu, a palette command and docs. Closed saved chats go to the reopen stack, which keeps 10.
- Risks: `closeTab` keeps a saved chat's draft text but drops its attachments (`drafts.forget()`), so attachment-only drafts count as at risk; a chat without a synced room must not be treated as idle; several worktree Keep/Remove dialogs can appear at once; more than 10 closed chats overflow the reopen stack.
- Recommended default: confirm every bulk close once, with Cancel as the default; leave Close other chats out at first.

### 6. Reorder Current chats (M, L with sort modes)
Order is the `tabs` array and already persists (`state/savedLayout.ts`). ⌘1-9 use that order and DESIGN keeps the numbers stable; unseen chats display above seen ones, so display order and numbers can already differ. The composer queue's grip-and-arrow-keys pattern (`QueueTray.tsx:172`) gives drag plus keyboard reordering without a new library.
- Recommended default: keep unseen chats first and keep shortcut numbers stable during automatic moves. A manual reorder changes the `tabs` order and therefore the shortcut numbers. Sort modes wait.

### 8. Several accounts per provider (M each, L together)
omp 18.16 already stores several accounts per provider (a new identity adds a row), keeps a session on one account, rotates to a sibling account at usage limits, and offers `/session pin <n|email|id>` and `task.agentAccountPools` for helpers (strings confirmed in the 18.16 bundle; `omp usage accounts` exists). The app can add an account picker in the chat menu that sends `/session pin` (M) and an account list in the helper editor that writes `task.agentAccountPools` (M). A choice per task, and pinning before a chat's first turn, need omp upstream.
- Risks: browser sign-in may reauthorize whichever account the browser is signed in to; today's Sign out (`omp auth-broker logout`) removes every account of a provider; a pin is refused while omp is replying.
- Owner: per-account Sign out through omp's RPC `logout` (this changes the AGENTS.md rule that names `auth-broker logout`); whether to ask omp upstream for per-task accounts.

### 9. Speed and animation polish (M first, L overall)
There is no profiling today beyond the status bar's CPU and RAM. Likely sources, not yet measured: each collab update re-renders about 31 subscribers, layout-animated list rows re-measure on every render, helper progress copies maps and rebuilds the helper list in three places, several whole-chat scans run per new entry, and the Tasks pane re-parses helper files every 2 s. The first step is measurement only: long-frame and React Profiler logging in development builds, and a replay of a 1,400-entry chat with four helpers through the scripted fixture under a CDP trace. Fixes are chosen from those numbers.
- Owner: target numbers; whether some row-sliding animations can go.

### 10. Status bar customization (L)

Session cost needs a running sum (M); omp's own CPU and memory need process sampling (M to L).
- Owner: which items can't be hidden (omp status and the update notice carry recovery actions); which metrics; one layout or per project.

### 11. Chrome profiles (L)
omp's relay extension identifies itself only with a random instance id, with no profile name or email, and one relay port can serve several profiles, choosing among them arbitrarily. Relays on different ports stay separate, so tying a project to a profile through its own port (`browser.relay` and `browser.relayUrl` in the chat's settings overlay), checking `/json/version` before omp uses the browser, and opening the right profile with `open -na "Google Chrome" --args --profile-directory=<dir>` (Windows `chrome.exe --profile-directory`) may work without an omp change [INFERENCE: launch, port assignment and wrong-profile behavior are untested].
- Found today: Chrome's `Local State` (profile names and accounts) cannot be read from this shell (macOS refuses with "Operation not permitted"); the packaged app would likely need the macOS permission to access other apps' data [INFERENCE]. The extension must be loaded by hand in each profile, since Chrome 137 removed `--load-extension` from official builds.
- Upstream for a verified identity check: the extension reports its profile, the relay lists connected browsers, and a setting routes new tabs only to a named profile.
- Owner: per project only, or with a per-chat override; ship the port convention now or wait for omp; on a mismatch, block or warn; may the app open Chrome windows itself.

### 12. Helper conversations (L, XL with live replies)
Today a helper's conversation opens in a dialog that fetches its file once over collab, renders replies as Markdown with tool-name chips only, and never updates while open; the Message action sends a steer without confirmation. omp's terminal focuses a helper in the main view (Esc returns). The work splits out a transcript body that does not depend on the session controller, adds a helper focus view in the chat column, follows the helper's local file with the existing tailer, and adds a composer that sends to the helper and reports errors. Word-by-word helper replies need the app's omp extension to listen for helper events, or omp to forward them.
- Owner: focus inside the chat (as omp does) or a drawer; whether a message steers immediately or queues; nested helpers.
