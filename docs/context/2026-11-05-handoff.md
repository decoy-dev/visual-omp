## Windows switch to Scoop

The switch quits visual-omp and runs a PowerShell script: add the decoy-dev bucket if needed, install or reuse a Scoop copy (user root, `SCOOP`, `SCOOP_GLOBAL`, ProgramData or Scoop's `global_path`), verify the executable, install record and manifest version, then run a temporary copy of the old uninstaller with `/S /KEEP_APP_DATA --updated _?=<dir>` and open the Scoop copy. An install failure keeps and reopens the installer copy; a cleanup failure opens the verified Scoop copy and reports what remains. `scripts/dev/scoop-switch-script.mjs` prints the script for given paths, with `-DryLaunch` to skip the final launch.

Tested on 2026-11-05 in the owner's Parallels VM "Windows 11" (ARM64, x64 emulation, user `chrishaddox`, Scoop and Git installed). The VM is encrypted: `prlctl exec` asks for the VM password on standard input, and `--current-user` runs as the signed-in user; the owner supplies the password. The Mac home folder is shared as `\\Mac\Home`. A test installer of the branch was cross-built on macOS with `npx electron-builder --win nsis --x64 --publish never -c.npmRebuild=false -c.extraMetadata.version=0.7.6`. The app in the VM can be driven over CDP by launching it through a scheduled task with `--remote-debugging-port=9229` and running a small Node CDP script inside the VM, since this Mac has no Accessibility permission for input. Results: the script alone against the released 0.7.6 installer copy, an end-to-end run from the app (profile kept, setup not shown again, installer copy and its registry entry removed, Scoop copy started), a cleanup failure with a locked file (uninstaller exit 2, folder restored, Scoop copy chosen) and a copy found only through `global_path` (reused, no second install). A leftover Scoop folder from a failed `scoop uninstall` fails verification and keeps the installer copy. The VM test state was cleaned up afterwards.

## Windows freezes since 0.7.6 (open)

The Windows user reports two freezes that ended in crashes since 0.7.6, with two chats, while typing or while the app ran behind Chrome. No root cause is confirmed; 0.7.7's diagnostics exist to capture one.

- The 0.7.6 change that only Windows received is the omp screen (TSP) as the default, with node-pty's bundled ConPTY for those hosts (`9dac1c0`).
- macOS measurements (production build, isolated profile, a throwaway provider streaming about 50 text chunks a second, window hidden): the renderer used 63-87% of a core with the omp screen and 76-92% with the classic terminal, so the omp screen was not heavier here. Memory returned to baseline when streams ended (main 70-200 MB, renderer heap about 70-80 MB); no leak appeared in 5 minutes. A development-build CPU profile of the hidden renderer showed React rendering the transcript while hidden, with garbage collection near 20%.
- WinFreeze's ranked hypotheses (read-only analysis): (1) presentation overload, since main publishes every 16 ms without a renderer acknowledgement and changed text nodes carry their whole growing text (`host.ts:495-518`, `main/ipc.ts:40-44`, `shared/tsp/patch.ts:28-31`); (2) live-preview watcher bookkeeping without cardinality limits during file storms (`preview-watch.ts:299-343`); (3) a native fault in the bundled ConPTY (node-pty issue 983, double kill heap corruption, which the app already avoids on exit); (4) uncapped buffers for malformed TSP frames (`tsp/stream.ts`).
- Next steps: once the user runs 0.7.7, read their Sentry events and memory samples; ask them to try Settings > Advanced > Classic omp terminal for a day as a comparison; consider pausing transcript rendering while the window is hidden and bounding presentation delivery to one outstanding revision (backlog item 9 measures first).
